# AgentMate V1.0 Release Candidate 门禁与试用方案

本文件是 V1.0 候选版本的单一验收入口。它不替代各专项测试，而是规定何时可以把它们汇总为
“工程候选版”“可试用候选版”或“可生产发布版”。未执行的层级不得记为通过。

## 1. V1 产品边界

目标用户是需要让 AI 在本机持续完成真实知识工作、又不愿把凭据和工作文件交给云端执行环境的个人及小团队。
V1 的核心定位是 **local-first AI 执行工作台**，不是通用聊天壳，也不是确定性实时控制系统。

本轮冻结三条黄金路径：

1. **从需求到成果**：创建任务或会话，调用真实工具生成可重新打开、可检查的 Artifact。
2. **从工作项到验收**：在项目中形成 WorkItem → Run → Artifact → 接受/退回的可追溯闭环。
3. **从定时触发到通知**：创建自动化，到点真实执行，保存运行记录并允许查看、重试或处理失败。

目录运营、更多连接器、评论/@提及/在线状态等不再阻挡 V1 候选版。生产桌面更新的域名、CI 私钥、
代码签名证书和跨版本升级证据继续由 WB-283 约束。

## 2. 一条命令、分层判定

在仓库根目录执行：

```powershell
# 仓库内工程门禁
pwsh -NoLogo -NoProfile -NonInteractive -File scripts/validate-v1-rc.ps1

# 已启动隔离测试后端且配置真实 LLM 时，再加入真实功能门禁
pwsh -NoLogo -NoProfile -NonInteractive -File scripts/validate-v1-rc.ps1 -Live

# 自动在临时目录与随机端口启动隔离 Server/Backend，跑完后清理
pwsh -NoLogo -NoProfile -NonInteractive -File scripts/validate-v1-rc.ps1 -IsolatedLive

# 本机具备 Rust 工具链时，加入 Tauri 编译预检
pwsh -NoLogo -NoProfile -NonInteractive -File scripts/validate-v1-rc.ps1 -DesktopPreflight
```

也可执行 `pnpm validate:v1-rc` 进入默认工程门禁。工程测试集合来自 Git 已跟踪/已暂存文件，避免把工作区中
尚未纳入版本的测试草稿误当成发布内容；脚本仍会针对这些正式测试读取当前工作树代码。脚本只汇报选中的
门禁；未选择的 live/desktop 层会显示 `NOT RUN`，服务、LLM 或工具链缺失会显示 `BLOCKED` 并以非零状态退出。
`-IsolatedLive` 不复用开发数据库或工作区，结束时会终止临时服务并删除临时目录；真实 LLM 必须通过
临时测试账号的模型管理 DB 配置，不能依赖 `backend/.env`。

| 层级 | 自动检查 | 通过后可以声称 |
|---|---|---|
| Engineering | issue 一致性、App/Console 类型与构建、Backend/Server 回归、隔离 HTTP 集成、Python 编译 | 工程候选版 |
| Live | 健康接口确认后端，功能套件 A–E 使用测试账号 DB 中的真实模型 | 本机真实功能候选版 |
| Desktop preflight | Tauri Rust 编译检查 | 桌面源码可编译；**不等于安装包验收** |
| Desktop release | sidecar/安装包、签名、干净 Windows 安装、启动与退出、升级/回滚 | 桌面可发布候选版 |
| Pilot | 下述真实用户连续证据 | 可进入受控发布决策 |

## 3. 桌面发布检查

桌面发布层按 [`desktop-build.md`](desktop-build.md) 构建 sidecar 和安装包，并在一台未使用开发仓库的
Windows 机器上执行安装校验。至少保存版本、安装包哈希、签名状态、主程序/sidecar 健康、三条黄金路径、
卸载结果和旧数据兼容证据。生产 updater 还必须完成 WB-283 的 HTTPS、可信代码签名和前后版本升级/回滚。

## 4. 小范围真实试用包

建议先进行 5 个工作日、3–5 名目标用户的受控试用。参与者只获得明确标记为试用版的安装包和一页任务卡：

- 用自己的真实资料完成一次“需求到成果”，确认产物可用；
- 在一个真实项目中交付并接受/退回一次工作项；
- 创建一个至少跨越 10 分钟的定时自动化，核对到点执行、通知和运行记录；
- 记录每次失败是否能理解、重试和恢复；不得收集 LLM 密钥、工作文件或会话正文。

每位参与者结束时记录：角色、系统版本、三条路径是否完成、首次有效成果耗时、人工救援次数、阻断问题、
继续使用意愿（1–5）和一句最需要改善之处。试用数据只保存聚合指标与用户主动提交的问题说明。

建议的 Go/No-Go 条件：

- 3 条路径总体完成率不低于 80%，且每条路径至少被 3 名用户真实完成；
- 定时触发成功率不低于 95%，失败均留下可见记录；
- 关键数据丢失、跨用户越权、密钥泄露为 0；
- 不依赖开发者直接改库或改文件，阻断级问题为 0；
- 至少 60% 参与者给出 4–5 分继续使用意愿。

不满足时回到对应 issue 修复并重跑受影响路径，不用新增功能抵消可靠性问题。

## 5. 当前边界与退出条件

- WB-307 已修复 Console 项目说明误显示 `[object Object]`，并以契约测试及明暗主题真实页面验证。
- WB-339 负责这套统一门禁和试用入口；它关闭只代表门禁可重复执行，不代表 live、桌面发布或 pilot 已完成。
- WB-283 是生产桌面更新的明确外部阻塞项，在材料和基础设施未提供前保持 deferred。

V1 可称为“可试用候选版”的最低条件是 Engineering、Live、Desktop release 全部有本次提交/版本对应证据；
V1 可进入受控发布决策还需要 Pilot 达标。任何一层只要是 `NOT RUN` 或 `BLOCKED`，结论必须保留该限定。
