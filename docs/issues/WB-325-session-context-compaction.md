## 问题

`_build_llm_messages` 每轮读取 `db.list_messages(session_id)` 并把全部 user/assistant 正文重新发送给
LLM。`CONTEXT_WINDOW` 当前只用于计算用量百分比，没有滑动窗口、持久化 Session 摘要或压缩触发门槛。
会话持续变长后，请求体和推理成本无界增长，最终可能超过模型上下文限制。

## 触发场景

1. 用户在同一个会话中持续多轮对话或执行长任务。
2. 每轮 user/assistant 正文都持久化到 `messages`。
3. 下一轮重新加载完整历史，不区分近期原文与可压缩的旧消息。
4. Token 使用逼近模型上限时仍继续组装全部历史，导致延迟、费用或请求失败。

## 影响

P1：会话是所有聊天、项目执行和助理渠道的共同基础；无界上下文会影响可靠性和成本，也会让新加入的
用户级、项目级和工作空间记忆与冗长历史争抢上下文预算。

## 建议修法

1. 为 Session 增加持久化滚动摘要及“已摘要到哪条消息”的游标，迁移存量时保持为空。
2. 上下文组装采用“系统提示 + 分层记忆 + Session 摘要 + 最近原始消息 + 当前消息”。
3. 根据可配置 Token 预算选择最近完整轮次；达到阈值后，用当前真实 LLM 对旧消息生成结构化事实摘要，
   原始消息仍完整留库，不删除、不伪造。
4. 压缩失败时安全回退到确定性的最近消息窗口，不阻塞本轮；工具 trace/引用文件继续只留历史展示，
   不重复喂入模型。
5. 对同一 Session 的摘要更新串行化，并保证重试/幂等 Run 不重复推进摘要游标。

## 验证

- 数据库迁移幂等，存量 Session 可读取；摘要和游标跨进程持久化。
- 小会话保持现有完整历史语义；超预算时仅旧消息被摘要，最近完整轮次和当前消息保留。
- 摘要失败时仍能构建有界上下文；并发同 Session 不发生游标回退或重复压缩。
- 项目/普通/助理会话、SSE、ask_user、stop、重试和历史回放不回归。
- `py_compile`、相关后端回归与真实聊天请求通过。
