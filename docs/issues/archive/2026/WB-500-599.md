### 问题

Server 已能按 WorkItem 返回关联 Run、执行状态、产物和验收记录，App 也已使用该投影；Console 项目工作台仍只展示计划与协作字段，缺少同一 WorkItem 的执行过程、结果、错误和验收入口。

### 触发场景

管理者在 Console 打开已交给 Local Agent 的任务，无法判断它是排队、执行、等待授权、失败还是已待验收，也无法查看产物。

### 影响

P1。Console 无法完成“管理任务并观察执行”的基本闭环，App 与 Console 对同一任务呈现出不一致事实。

### 建议修法

在 Server 提供可分页的 WorkItem Run + Delivery 读模型，Console 任务详情增加执行区：最新状态、真实计划/步骤、设备、耗时、待用户动作、结果、产物、错误和验收。共用 App 的状态语义，仅展示 Server 已接收和脱敏内容。

### 验证

- 同一 WorkItem 在 App 和 Console 显示同一 Run 状态、终态和产物。
- 排队、等待授权、失败、重试和已验收可区分，无计划时不伪造百分比。
- Viewer 只读；本机私密路径、凭据和未上传输出不出现。

### 处理记录

- 2026-08-11：根因确认。Server 的 WorkItem delivery 端点虽能返回关联 Run 与产物，但此前直接返回完整 Run 行，未形成适合 Console 的共享读模型；Console 也没有对应 API、类型与任务详情执行区，因此管理端看不到排队原因、真实计划、事件、设备、交付与验收事实。
- 2026-08-11：Server 将 delivery 改为稳定分页的字段白名单投影，补充 queue context、最近领取设备、结构化计划、允许共享的 Run 事件、产物校验与验收记录；明确排除 `request_snapshot`、`permission_snapshot`、checkpoint 等本机执行细节，并对事件中的本机路径及凭据样式文本做脱敏。
- 2026-08-11：Console 任务抽屉新增「Local Agent 执行与交付」区域，按真实状态展示排队/执行/等待用户/暂停/恢复/失败/待验收/已验收，展示计划步骤、最近事件、设备、耗时、模型用量、错误、不可变产物下载和有权限的整批验收入口；无计划时明确显示空态，不伪造进度百分比。
- 2026-08-11：自动验证通过：`server/tests/test_wb500_console_execution_projection.py` 与既有 `test_wb461_server_work_item_execution.py` 共 5 个用例通过；Console `npx tsc --noEmit` 与 `npx vite build --config vite.console.config.ts` 通过。
- 2026-08-11：真实页面验证通过。使用隔离 Server/SQLite、真实 Run 协议事件和真实对象存储产物，在 Console 完成任务详情读取、产物下载入口呈现以及「验收全部产物并完成任务」状态闭环；深色、浅色、780px、390px 均无横向溢出，浏览器控制台无错误。Viewer 只读、事件白名单、路径/凭据脱敏与分页由服务端回归用例覆盖。
- 2026-08-11：边界保留。Console 只观察并验收 Server 已接收的共享事实；等待回答或授权时仍提示执行负责人回到 App 处理，不把远程 Console 变成本机工具控制面。

### 问题

Server Run 协议已支持多设备注册、心跳、能力匹配、容量和 `target_device_id`，但 Console 没有设备列表、实际 readiness 或在任务/自动化中指定执行设备的产品入口。

### 触发场景

同一账号注册了多台 Local Agent，其中只有一台具备目标 working copy 或私有连接器。管理者无法在 Console 选择该设备，也无法事前看到不兼容原因。

### 影响

P1。多设备协议能力不可用，后台任务可能长时间排队、选错设备或在执行后才暴露缺失能力。

### 建议修法

增加账号设备投影，展示设备名、在线、协议/App 版本、工具/Skill/连接器 readiness、容量和最近错误。任务和 Automation 使用 `specific | any_compatible`，并先固定 `execution_owner_id`；MVP 只允许选择该 owner 的已验证设备。

### 验证

- 两个独立 Local Agent 设备可同时注册，Console 显示真实心跳和能力差异。
- `specific` 仅由指定设备领取；`any_compatible` 只从同 owner 兼容设备中选路。
- 离线、撤销、不兼容、缺能力、容量满和写锁冲突都返回可解释原因。
- 多进程共用同一 SQLite/工作目录不被当成支持的多节点模式。

### 处理记录

- 2026-08-11：根因确认。Server 已有设备身份、心跳、能力匹配、租约容量与 `target_device_id`，但 `/api/devices` 只返回注册表原始行，Automation 也始终写入空目标；Console 因而既没有可操作的设备就绪投影，也不能把执行固定到某台设备。
- 2026-08-11：Server 设备投影新增验证、在线、核心协议兼容性、并行/驻留容量、最近失败与 `ready / busy / offline / incompatible / unverified / revoked` 就绪状态；继续由现有 queue context 对离线、撤销、能力不匹配、容量满、等待确认和工作区写锁给出真实原因。
- 2026-08-11：Automation 新增持久化的 `routing_mode` 与 `target_device_id`。`specific` 只接受执行 owner 名下已验证且未撤销的设备，`any_compatible` 保持空目标；调度创建 Run 时写入稳定路由，执行 owner 仍固定为自动化 owner，不因设备选择改变。
- 2026-08-11：Console 新增 Local Agent 管理页，展示设备身份、真实心跳、协议/App/平台版本、能力与工具、容量、最近错误并支持撤销；自动化新增“任一在线兼容设备 / 指定 Local Agent”选择与保存回读，并明确提示多副本必须使用独立数据目录和工作副本，不支持共享 SQLite 或同一可写工作区的多进程模式。
- 2026-08-11：自动验证通过。`test_wb501_device_routing` 覆盖两台设备的 specific/any-compatible 领取、设备投影及未验证目标拒绝；连同自动化调度、设备协议、排队原因和 schema migration 共 20 个用例通过。Console `npx tsc --noEmit` 与 `npx vite build` 通过。
- 2026-08-11：真实页面验证通过。隔离 Server/SQLite 中注册一台在线和一台离线设备，Console 正确显示就绪、离线、心跳、并行/驻留容量和工具能力；在自动化表单选择指定设备并保存后，列表稳定回读该设备。深浅主题切换正常，1280px 页面无横向溢出。浏览器只出现仓库既有的 Ant Design deprecated API 开发警告，无业务请求或渲染异常。


</details>

### 问题

Console 已有定时、interval 和 Webhook Automation，但这些 fire 创建的 Run 不绑定 WorkItem。WorkItem 本身没有执行 owner、设备选路、能力门禁、幂等触发和自动重试策略，无法安全表达“这个任务就绪后由 Local Agent 自动执行一次”。

### 触发场景

管理者在 Console 创建任务并希望它自动执行；现在只能另建一条 Automation，执行结果不会自然进入该任务的 Delivery/验收闭环。

### 影响

P1。如果用布尔开关直接自动运行，会遗漏依赖、重复 Run、设备能力、后台权限和人工验收边界。

### 建议修法

为 WorkItem 增加结构化执行策略：`manual | auto`、execution owner、`specific | any_compatible`、目标设备、必需能力、超时/token/重试/通知和最小预授权。只在任务/Sprint/依赖/设备/readiness 门禁通过时幂等创建一个 Run，成功后进入人工验收。

### 验证

- 相同 WorkItem 版本的重复触发只创建一个 active Run。
- 依赖未完成、Sprint 未激活、设备离线/不兼容或高风险权限缺失时不启动，并有真实可观察原因。
- 重试创建带 `retry_of` 的新 Run；成功不自动把 WorkItem 置为 `done`。
- 与周期性 Automation 的语义、历史和幂等键明确分离。

### 处理记录

- 2026-08-11：根因确认。现有周期/Webhook Automation 只能按独立自动化定义创建 Run，WorkItem 没有执行 owner、设备路由、能力与权限门禁，也没有任务版本级幂等键和独立重试链，无法安全表达一次性交付。
- 2026-08-11：Server 新增持久化 WorkItem 执行策略与后台扫描器。策略包含 `manual / auto`、执行 owner、`specific / any_compatible`、目标设备、必需能力、超时、尝试次数、退避、token 上限、通知策略和最小预授权；策略状态和阻塞码直接挂到 WorkItem 投影。
- 2026-08-11：执行门禁覆盖任务状态、依赖、活动 Sprint、执行 owner 项目权限、设备验证/归属/在线/兼容/容量、同项目写锁与高风险权限。相同策略版本使用 `work-item-auto:<id>:v<version>:attempt:<n>` 幂等键，重复触发复用 active Run；失败重试创建带 `retry_of` 的新 Run。
- 2026-08-11：Run 继续使用既有 `projexec` 协议和 Delivery/产物验收链；执行成功只进入待验收状态，不自动把 WorkItem 标为 `done`，人工验收后策略才显示已验收。其状态、历史和幂等命名空间与周期性 Automation 完全分离。
- 2026-08-11：Console 任务执行面板新增一次性自动执行策略，支持模式、设备路由、目标节点、超时和重试配置，并显示真实的排队、运行、等待重试、门禁阻塞、待验收与已验收状态。
- 2026-08-11：自动验证通过。WB-502、WB-500、WB-501 与 schema migration 共 12 个用例通过，覆盖重复触发、依赖/Sprint/设备/权限门禁、带 `retry_of` 的重试以及成功后人工验收边界；Console `npx tsc --noEmit` 通过。
- 2026-08-11：真实页面验证通过。隔离 Server/SQLite 与 Console 中配置指定离线 Local Agent，任务详情稳定回读自动执行开关、指定设备、超时、最多尝试次数和“目标 Local Agent 已离线”门禁原因；深浅主题下策略面板均可见可操作，未产生虚假 Run。

### 问题

Console 已有项目数量、健康风险、任务负载和 Sprint 燃尽，但没有基于 Server Run/Delivery 的执行效率、质量、成本和设备资源投影。

### 触发场景

管理者想回答“近 7 天哪些任务排队最久、失败最多、首次验收最差、消耗最高、因设备能力阻塞”，Console 无统一数据口径。

### 影响

P2。不阻塞单次执行，但管理者无法定量判断 Agent 交付效果、成本和运行瓶颈。

### 建议修法

建立带项目/组织权限、时间窗口和口径版本的 Server 聚合 API，首批覆盖 Run 状态、排队/执行耗时、重试/成功、阻塞原因、首次验收、返工、产物校验、token/成本和设备能力/容量/WAL。Console 提供总览、趋势和下钻到真实 WorkItem/Run 的入口。

### 验证

- 聚合值可通过同一权限范围的 WorkItem/Run/Delivery/用量明细重算。
- 时间窗口、时区、重试、取消、未定价模型和未验收交付口径有版本化说明。
- Viewer 仅能看可访问项目；对个人凭据和本机私密数据不做聚合或下钻。

### 处理记录

- 2026-08-11：根因确认。项目概览只聚合任务和健康风险，真实 Run、租约设备、交付产物、验收与用量虽已在 Server 持久化，却没有统一的项目权限、时间窗口和指标口径 API。
- 2026-08-11：Server 新增 `project-execution-v1` 项目执行分析。API 强制复用项目访问权限，支持 7/30/90 天与 IANA 时区，返回精确 `[start,end)`；取消不进入成功率，排队中 Run 不进入耗时分位数，未定价成本单独计数且按记录币种分组。
- 2026-08-11：交付质量口径覆盖产物完整性校验、已验收交付、首次成功即验收和后续返工 Run；当前队列瓶颈直接由持久化设备/租约状态计算，设备仅投影项目 Run 已使用或指定节点的就绪与容量，不暴露其他本机数据。
- 2026-08-11：分析下钻只返回项目内 WorkItem/Run 标识、状态、耗时、token、预估成本和设备显示名；不聚合凭据、提示词、消息、事件载荷、错误详情、本机路径或私密文件内容。Viewer 可读可访问项目，非成员统一返回 404。
