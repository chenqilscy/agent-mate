  - backend/main.py:113

```

</details>

### 问题

Server 客户端使用顶层 `httpx.get/post/...`，每次请求新建 Client，pull 的多请求链不能复用连接；传输层直接抛
FastAPI `HTTPException`，后台调用难以区分永久 4xx 与可重试网络/5xx。App 又使用八个分散且已弃用的
`on_event` 处理器，缺少统一资源关闭与部分启动失败清理。

### 触发场景

多项目同步产生 `2+N` 个短连接；Server 409 在后台工作项交接中被折叠成普通失败并反复重试；导入 main 产生
八组 lifespan 迁移警告。

### 影响

P2。远程控制平面延迟与连接成本放大，错误重试策略漂移，应用资源生命周期难以审计。

### 建议修法

使用线程安全的共享同步 Client 与明确关闭入口；引入不依赖 FastAPI 的 Server 拒绝异常并由路由边界转换；后台按
永久拒绝/暂时不可达分类。将 startup/shutdown 收敛到单一 lifespan，失败时逆序清理已启动组件。

### 验证

连接 Client 被复用并在 shutdown 关闭；路由仍保留 4xx detail，后台永久拒绝终止、网络/5xx 重试；不再产生
`on_event` 弃用警告，启动/关闭回归通过。

### 处理记录（2026-08-04）

- 已认领：收敛现有 Server 通信与进程资源生命周期，不改变 API 功能。
- 改动：Server 调用统一复用线程安全同步 `httpx.Client` 并在 lifespan 关闭；传输层以独立 `ServerRejected` 区分永久 4xx 与暂时不可达，由 FastAPI 边界还原状态和 detail，后台永久拒绝终止、网络/5xx 保持重试；八个 `on_event` 收敛为单一 lifespan，部分启动失败与正常关闭均逆序清理。
- 验证：Client 复用/关闭、路由错误语义、后台分类和 lifespan 顺序/回滚相关回归 23/23；额外 lifespan 4/4 通过（含数据库启动失败清理），导入确认 startup/shutdown 旧注册表均为 0；backend regression 324/324 通过。
- commit：待本次归档提交。

### 触发场景

### 影响

### 建议修法

### 处理记录（2026-08-04）

- 已认领：仅加固既有 SSE 事件集合和 payload 最低契约，不增加事件类型。
- 改动：TypeScript 联合类型增加唯一运行时事件名表；解析器拒绝未知事件、畸形 JSON 和缺少最低必需字段的 payload，并转为显式 SSE error；chat store 增加 `never` 穷尽分支；新增 Python/TypeScript/store 三方事件名契约测试。

### 问题
`PePanel` 从 assistant message trace 和文件 diff 临时推导“产物”，没有读取后端已经持久化、带校验与验收状态的 Run Artifact 清单；diff 还会被提升成“工作空间产物”。同一交付在历史回放、trace 缺失或验收状态更新后可能与权威记录不一致。

### 触发场景
一个 Run 写入多个文件并生成 Artifact，随后验收其中一个产物或重新打开历史 Session → 右侧结果区仍按消息 trace/diff 重建，无法保证与 `/runs/{run_id}/artifacts` 一致，也没有稳定的主产物聚焦规则。

### 影响
结果区是交付验收入口。非权威数据会让用户看到过期状态或把普通变更误认为交付产物，削弱 Run/Artifact 交付闭环。

### 建议修法
从当前消息确定最近 Run，以 `listRunArtifacts` 为唯一权威源；流式期间在 Artifact trace 变化后刷新。仅在没有 Run 的遗留会话回退到真实 Artifact trace，不再把 diff 当作产物。使用稳定顺序选出主产物，并在没有用户已打开文件时自动聚焦。

### 验证
- 前端单元测试覆盖最近 Run 选择、Artifact 权威映射和遗留回退。
- `npx tsc --noEmit` 与生产构建通过。
- 历史会话、流式新增 Artifact 和验收状态刷新时结果区均来自后端清单。

### 处理记录（2026-08-04）
- 改动：`PePanel` 改为按最近 Run 请求 Artifact 权威清单，Artifact trace 仅作为 API 失败或无 Run 遗留会话的保守回退；普通 diff 不再提升为产物；完成态自动聚焦稳定排序的首个产物。后端 Artifact 排序增加 id 兜底，保证同时间戳顺序稳定。
- 验证：327 项后端回归与 TypeScript project build 全部通过，主应用及 Console 生产构建通过；在真实历史项目页面验证“变更 (2)”存在而产物区保持空态，并完成明暗双主题视觉检查。
- commit：待提交

<details>
<summary>原始元数据</summary>

  - backend/agent/runtime.py:1

```

### 问题

现有 AgentMate 仍以“local-first 应用 + Server 控制平面”为正式架构：本地 backend 同时承担业务数据权威、Server 客户端、镜像合并、离线回退和 Agent 执行，Server 只覆盖部分协作实体。项目、成员、任务、目录和时间线因而需要 `origin`、`server_updated_at`、`server_dirty`、冲突台账、条件 pull、写代理与 outbox 等多套一致性机制。

产品目标现已调整为 **Server-first**：Server 应成为所有持久业务数据的唯一权威；本地只保留设备绑定的秘密、权限、执行工作区、运行时进程、可靠事件 WAL 和可重建缓存。现有架构文档、数据分层规范与实施路线尚未表达这一目标，也没有可分阶段迁移和独立验收的工作包。

### 触发场景

1. App 读取或修改一个协作实体时，需要先判断 Server 是否配置、Bearer token 是否存在以及项目是否为 `origin="server"`。
2. 读取成功后还要镜像到本地数据库；写入成功后重新 pull，Server 不可达时还要在“缓存读取、失败、纯本地回退”之间分支。
3. 新增会话、Run、自动化、频道、资产等实体时，必须再次决定本地/Server 双份数据、同步方向、冲突和离线语义，复杂度持续扩张。

### 影响

P1：双权威模型增加数据丢失、权限漂移、离线假成功和跨端不一致风险，也阻碍 Server、Console 与桌面执行端形成清晰的产品边界。若继续在旧模型上扩展功能，后续迁移成本会继续上升。

### 建议修法

1. 编写正式 Server-first 目标架构，明确 Server（API + Console + 业务数据库/对象存储/Run 调度）与 Local Agent（Desktop UI + 后台执行服务 + Agent Runtime + 本机工具/安全存储）的责任边界。
2. 制定实体级数据归属矩阵：所有持久业务数据以 Server 为唯一权威；本地状态只能是设备秘密、执行工作集、WAL 或可重建缓存。
3. 定义 Run 租约、事件序列、ACK、断线续传、取消与设备失联语义，避免把可靠事件上传重新做成通用业务数据同步。
4. 明确离线边界：允许已领取 Run 继续执行并缓存事件，不允许离线创建或修改 Server 业务对象。
5. 制定兼容迁移、幂等导入、回滚观察期和旧镜像同步退役顺序，并拆分为可独立验收的子 issue。

### 验证

- 新架构文档明确组件边界、信任边界、数据归属、主调用链、故障语义、迁移阶段和回滚策略。
- 数据分层规范不再把 App 本地数据库描述为业务权威，并清楚区分业务数据、执行工作集、秘密、WAL 与缓存。
- 每个迁移阶段都有独立 issue、依赖关系、验收条件和“旧机制何时可以删除”的退出门槛。
- README/AGENTS 等入口文档能够指向新目标架构，同时明确当前实现仍处于迁移期，避免把设计目标误报为已完成。

### 问题

父项：[WB-431](archive/2026/WB-400-499.md#wb-431)，依赖 WB-432 的 Run schema。现有 relay 只支持外部事件租约，没有 Local Agent 设备注册、Run fencing、顺序事件 WAL/ACK、取消和断线续传的完整协议。

### 触发场景

Local Agent 执行中断网、崩溃或发生双 worker 竞争时，Server 不能以统一协议确认哪一个执行者有效，也不能证明事件不丢失、不重复生效。

### 影响

P1：没有可靠执行通道就不能把 Run 权威迁入 Server，也不能安全支持后台或 headless Local Agent。

### 建议修法

- 建立 device registration、密钥 challenge、capability report、heartbeat 和撤销。
- 建立 `lease_id/lease_epoch`、续租、超时、fencing、取消和 checkpoint 语义。
- 定义 `event_id + run_id + lease_epoch + seq`、本地 WAL、Server 去重和连续 ACK 高水位。
- 支持 seq gap 补传、容量门禁、ask_user 往返和协议版本兼容。

### 验证

- 覆盖断网重连、重复发送、Server/Agent 重启、租约过期和双 worker 竞争。
- 没有重复工具副作用；Server 事件序列无缺口，Local WAL 只在 ACK 后清理。
- 撤销设备和旧 epoch 不能领取或提交新的执行结果。

### 处理记录

- 2026-08-08：确认既有 `/api/relay` 是外部 automation webhook relay，不承担 Server-first Run 执行；新增独立设备/Run 协议，未改变旧 relay 契约。
- Server migration v11 建立 `agent_devices/device_challenges/device_tokens/run_leases/run_events/run_commands`，并给 `business_runs` 增加目标设备、capability、输入快照、epoch、恢复次数和 cancel version。设备使用本机 Ed25519 私钥完成五分钟一次性 challenge；Server 只存 public key 和 Device token hash，账号暂停、设备撤销或 token 过期均 fail closed。
- `/api/agent/runs/lease` 在 `BEGIN IMMEDIATE` 内原子领取，数据库唯一索引保证一个 Run 只有一个 active lease；重领递增 `lease_epoch`，所有续租/事件/命令请求均校验当前设备、lease id 与 epoch。租约超时或设备撤销进入 `recoverable`，超过恢复上限由 Server 提交失败终态。
- Server 对 `event_id` 与 `(run_id, lease_epoch, sequence)` 双重去重并校验 canonical SHA-256；只接受连续序列并返回 `ack_high_water`。terminal、checkpoint、`ask_user`、answer command 和 cancel/ack 都先持久化再响应，重复发送不重复生效。
- Local migration v9 建立 `run_transport_leases` 与 `run_event_wal`。事件先原子写 WAL；网络失败、进程重启或 gap 都保留原 envelope，只有 Server 连续 ACK 才删除。WAL 达容量上限抛出 `WalCapacityExceeded` 阻止继续产生事件，不静默丢弃；无法补齐的 gap 或旧 epoch 使本地 lease 进入 `fenced`。
- scheduler 目前只做设备注册、capability heartbeat 和 WAL 补传，不主动领取 Run；真实执行 owner/IPC 接管留给依赖项 WB-434，避免协议上线后误消费任务。设备私钥仍在 backend-only `device_secrets`，不进 UI、日志、WAL 或 Server；迁入 OS secure storage 随 WB-434 本机服务边界完成。
