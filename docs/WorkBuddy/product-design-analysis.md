# 腾讯 WorkBuddy 产品设计分析与 AgentMate 对标

> 基于 [官方资料索引](official-sources.md) 和本地
> [高保真参考原型](tencent-workbuddy-reference.html) 整理。官方事实、AgentMate 现状与本项目建议
> 分开表述；涉及腾讯内部技术实现的内容仅在官方明确披露时作为事实，否则均视为产品层推断。

## 1. 产品公式：任务操作系统，不是聊天机器人

WorkBuddy 的主对象是“任务”：用户选择工作目录、模式、模型、Skill 和连接器后，用自然语言描述
目标；Agent 拆解步骤、调用工具、持续修正，并把文件、页面、数据结果和执行记录作为交付物。

这套设计把体验重心从“回复是否像人”转向三个可验收问题：

1. 是否理解了目标并形成可审阅计划；
2. 是否在明确权限边界内完成真实操作；
3. 是否产出能打开、检查、继续修改或复用的结果。

对 AgentMate 的直接要求是：新增卡片或提示词不能算新增能力；必须同时具备真实工具、运行时调用、
产物保存、过程事件和验收路径。

## 2. 信息架构与能力分层

| 层级 | WorkBuddy 产品职责 | AgentMate 当前对应 | 判断 |
|---|---|---|---|
| Tool | 文件、浏览器、脚本、外部 API 等最小执行动作 | 5 个基础工具、4 个 Skill 工具、项目/知识库条件工具和 MCP 工具 | 基础闭环存在，但办公产物和浏览器能力明显不足 |
| Skill | 指令、脚本/工作流、工具和资料组成的可安装能力包 | Server `APP_SKILLS` + 本机目录快照 | 定义/安装已真实化，发布、权限和兼容仍需收口 |
| Expert | 人设、领域方法论和工具链 | `catalog_experts` persona + loadout | 单专家可真实影响系统提示，但方法、工具和评测未形成版本包 |
| Expert Team | 团长拆解、多角色并行、汇总交付 | 一次把多个专家 persona 加入同一会话 | 目前不是多 Agent，应避免宣称并行专家团已经完成 |
| Connector | 外部系统的身份、授权、数据和写操作通道 | 内置 MCP + 第三方 stdio，凭据本机保存 | 架构方向正确；授权 UX、能力范围和更多办公系统待补 |
| Automation | 定时触发任务，绑定工作区、模型、Skill 和通知 | 本机自动化调度 | 已有真实执行；需强化无人值守权限、结果投递和审计 |
| Inspiration/Template | 通过案例发现价值，一键带入 Prompt 和能力 | 灵感/模板目录 | 展示层已有；必须保证“做同款”引用真实可用能力 |
| Enterprise control plane | 身份、组织、目录、Agent Manifest、渠道、凭据、运行和评测治理 | AgentMate Server + Console | 已有控制面骨架，能力发布/Test Run/评测/灰度仍不完整 |

## 3. 核心用户流程

### 3.1 首次价值：一句话启动真实任务

入口不是复杂流程编辑器，而是任务输入框。模型、Skill、连接器和工作目录在输入区附近按需展开，
降低启动门槛。模板与灵感负责提供“我可以让它做什么”的具体例子。

AgentMate 应保持同样的渐进式披露：默认只要求目标，复杂任务再显式选择 Plan、项目工作区、专家、
Skill 和连接器；不能让用户先理解所有能力名词才能开始。

### 3.2 执行信任：计划、权限和过程可见

Ask/Plan/执行模式把风险预期放在任务开始前；工作目录限制文件范围；过程中展示步骤、文件读取、
变更和产物。连接器再以独立授权控制外部系统。

AgentMate 已具备 SSE 真实事件和项目沙箱，但需要继续把风险做成结构化契约：工具读/写/网络/外部
服务范围、是否需要确认、是否适合无人值守、审计内容和敏感字段脱敏。

### 3.3 完成交付：右侧结果区而非聊天附件堆积

任务执行记录回答“发生了什么”，结果区回答“交付了什么”。文件预览、网页预览、全部文件和变更
需要长期稳定地指向工作区产物，而不是埋在某条消息中。

AgentMate 后续补充 DOCX/XLSX/PPTX/PDF/图片工具时，应把“生成 → 渲染 → 视觉检查 → 修正”作为
工具和 Skill 验收的一部分，并在统一产物区展示可下载文件和预览。

### 3.4 能力增长：发现、安装、使用、更新、复用

Skill 市场解决发现与安装，专家/专家团解决任务角色选择，灵感解决案例转化，自动化把成功任务变成
周期执行。企业控制面再把个人成功经验发布给组织。

AgentMate 当前目录、推荐位和安装已经分开，但还缺“发布版本 → 客户端兼容 → 安装快照 → 权限确认
→ 更新/回滚”的完整生命周期；这是 Console 从目录 CRUD 走向能力运营平台的关键。

## 4. 本地执行与中心控制面的边界

从产品行为可观察到 WorkBuddy 同时覆盖本地授权目录、远程渠道、自动化和企业治理。对 AgentMate
不应简单照搬其云端范围，而应坚持现有 local-first 取舍：

- 工作区文件、会话正文、LLM Key 和连接器 secret 留在 App 本机；
- Server 管账号、组织、项目协作、公共能力定义、发布状态和兼容策略；
- Console 是 Server 的管理界面，不成为第三份数据权威；
- Server 可宣布目录变更，但不能凭目录数据凭空创造 App 没有实现的 Tool；
- App 不可达时使用最后可用快照，不能因临时离线丢失已验证能力；
- Server 显式撤回与网络不可达必须是两种状态，不能都解释成“回退本地 builtin”。

## 5. AgentMate 当前最重要的产品差距

### P0：能力发布与升级闭环

- Console 停用/撤回需要 tombstone，阻止同 slug builtin 复活；
- Skill 指令、工具、文件、权限、版本和哈希必须形成原子快照；
- App 上报版本与工具能力，Server 按最低版本和兼容策略发布；
- 纯内容且不扩大权限可自动升级，扩大权限必须重新确认；
- Tauri updater 需要正式 endpoint、签名 CI、灰度、强制最低版本和回滚。

### P0：真实办公交付工具

- DOCX 创建/编辑/渲染；
- XLSX 读取、公式、统计和图表；
- PPTX 创建、布局、渲染和检查；
- PDF 提取、生成、合并/拆分和渲染；
- 浏览器导航、交互、下载和截图；
- 文件搜索、补丁编辑、复制/移动/重命名/归档。

当前“Word 文档生成”只有结构化写作提示，“股票综合分析器”没有权威行情工具；在真实工具补齐前，
应按实际能力重命名或限制场景，不能让名称暗示已经能生成 `.docx` 或读取实时市场数据。

### P1：办公连接与多模态

优先建设邮箱、日历、企业文档与主流 IM；再补 OCR、图片生成/编辑、音频转写、深度研究和自动化
结果投递。每个连接器应独立授权，写操作明确确认，token 只存本机。

### P2：真实多 Agent 专家团

目标不是把多个人格拼进一个 system prompt，而是：团长拆解子任务 DAG、成员独立上下文并行执行、
结果交叉审阅、失败降级、预算控制、最终汇总，并能查看每个成员的真实工具事件和产物。

## 6. 不应照搬的部分

1. **动态商品数字**：模型、Skill 数量、连接器数量和套餐价格不能作为代码常量或验收条件。
2. **只有视觉没有能力的橱窗**：参考界面不等于复刻所有卡片；无真实运行时的卡片应隐藏或标未就绪。
3. **把中心控制等同于上传数据**：AgentMate 的 Server 运营能力不能突破文件、会话与凭据不上云的红线。
4. **用 `run_command` 代替所有工具**：通用 shell 难以表达权限、结构化输入输出、审计和跨平台兼容；
   高频办公能力应建设专用工具。
5. **把专家团当提示词集合**：只有真实拆解、并行、汇总和成本治理后，才应使用“多 Agent 专家团”描述。

## 7. 产品验收原则

任何新能力至少回答以下问题：

- 用户从哪里发现并理解它？
- 是否需要安装、连接或授权？
- Agent 得到了什么真实工具和指令？
- 读、写、网络和外部服务边界是什么？
- 运行过程如何观察、停止和恢复？
- 交付物在哪里，如何打开和验证？
- Server 更新后，旧 App 如何兼容、升级或回滚？
- 离线时使用什么最后可用状态？
- 是否有真实自动化测试和人工端到端验收？

缺少其中任一关键环节时，应在文档和 UI 中明确标注边界，不以“已支持”概括。
